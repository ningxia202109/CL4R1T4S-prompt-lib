## 1. 文档性质：这是什么类型的文件？

这不是一份"简短提示词"，而是一次对 **Claude.ai 网页/移动端聊天界面**完整运行时上下文的捕获（或重建），包含三大部分：

1. **系统提示词正文**（第 1–1589 行）：身份、产品信息、安全护栏、记忆系统、各类工具的使用规范。
2. **完整的工具 JSON Schema 列表**（第 1590–1665 行）：以 `<functions>` 块给出的 30 个可调用工具的原始 JSON 定义。
3. **运行时变量注入**（第 1667–1679 行）：`current date`、`<profile>(not yet written)</profile>`、`<memory_listing>{MEMORY_LISTING_ENTRY_REDACTED}</memory_listing>`。

第 3 部分是关键证据：`{MEMORY_LISTING_ENTRY_REDACTED}` 这种占位符是**典型的"脱敏后公开"处理方式**——如果是纯粹虚构/AI 生成的文档，没有理由去脱敏一个不存在的用户记忆列表。这强烈提示本文档的骨架**很可能源自一次真实的会话捕获**，而不是从零编写的虚构文本（详见第 8 节"真实性评估"）。

## 4. 安全护栏体系：分层与重点

整份文档的安全设计是**分层防御**，而不是单一规则清单：

1. **绝对红线**（不可被任何框架/角色扮演绕过）：儿童安全、CBRN 武器细节、恶意代码。儿童安全部分有一条很有辨识度的规则——"如果发现自己在心理上给请求做'合理化重新框定'，这个动作本身就是拒绝的信号"，即**元认知层面的自我审查触发器**，而不是关键词过滤。
2. **默认帮助、按需拒绝**（`<default_stance>`）：只有"具体、明确的严重伤害风险"才拒绝，边缘/尴尬/假设性请求不构成拒绝理由——这是偏"宽松"的默认值，与很多同类文档偏保守的基调不同。
3. **用户福祉红线**：疑似自杀倾向/进食障碍时，**主动回避**具体方法细节、避免精确热量数字，即使是"纯粹研究/资讯"语境也要在回答末尾加一句敏感提示。这里还有一条很具体的资源更新要求——"用 National Alliance for Eating Disorders 热线而不是 NEDA，因为 NEDA 已永久关停"，说明该文档试图反映"知识截止后才发生"的具体事实变化。
4. **政治/伦理议题的"呈现双方"要求**（`<evenhandedness>`）：要求 Claude 输出"辩护方会给出的最佳论证"而非自己的观点，且**结尾必须补充反方观点**，即使 Claude 本身认同该立场——这是防止"单方面说服"被滥用的结构性设计。
5. **`suggest_research` 工具里的个人隐私红线**：对"某个非公众人物的具体病情预后/生存率""某个私人的调查"等请求，**明确禁止**推荐"深度研究"功能（哪怕文献本身是公开的），理由是"针对私人个体的汇编报告"本身就是伤害——这是把"是否为公众人物"和"请求的锚点是通用议题还是特定个人"作为唯一判据，而不是看资料来源是否公开。

## 5. 完整工具清单：30 个工具的能力地图

`<functions>` 块（第 1590–1665 行）给出的原始 JSON Schema，按功能归类：

| 分类 | 工具 | 关键约束 |
|---|---|---|
| **记忆管理**（6） | `memory_read` / `memory_write` / `memory_str_replace` / `memory_append` / `memory_list` / `memory_delete` | 均要求 `if_version` 乐观锁；每个写入类工具的 description 里都**内嵌一份隐私黑名单**（种族/性取向/健康诊断/政治立场/精确金额/家庭住址/伴侣子女姓名/证件号码），与系统提示正文的 `<privacy_requirements>` 完全独立、重复设防 |
| **容器文件操作**（4） | `bash_tool` / `create_file` / `str_replace` / `view` | `str_replace` 明确要求"编辑后必须重新 view，之前的 view 输出已过期"；只读挂载目录（uploads/skills 等）不可直接编辑 |
| **信息检索**（5） | `web_search` / `web_fetch` / `image_search` / `conversation_search` / `recent_chats` | `web_fetch` **只能抓取对话中已出现过的 URL**（用户给的或搜索/抓取返回的），不能凭训练记忆拼 URL；`conversation_search` 明确是"文本匹配"而非语义检索 |
| **结构化产出/小组件**（5） | `recipe_display_v0` / `places_map_display_v0` / `message_compose_v1` / `visualize:read_me` / `visualize:show_widget` | `visualize:show_widget` 要求先静默调用 `read_me` 加载设计规范，且"严肃话题（疾病/战争/死亡等）的 loading 文案必须无聊化，禁止用戏剧化措辞"——是一条很细腻的语气分级规则 |
| **垂直领域数据**（3） | `fetch_sports_data` / `weather_fetch` / `places_search` | 体育数据工具要求"先查比分再查详细数据再回复"的强制顺序；地点搜索要求 `place_id` 必须逐字复制不能凭记忆输入 |
| **连接器/生态引导**（3） | `search_mcp_registry` / `suggest_connectors` / `recommend_claude_apps` | 三者构成一条"先搜索目录→再展示选项→等用户选择"的强制流水线，**不允许**跳过中间步骤直接调用第三方连接器（除非用户明确点名） |
| **会话/产出控制**（4） | `ask_user_input_v0` / `end_conversation` / `present_files` / `suggest_research` | `suggest_research` 的 description 长达数百字，专门规定"结尾必须是本工具调用、之前不能有'要不要我...'式征求同意的话术"——把"渲染按钮=用户的同意"这一原则写得极细 |

**观察**：这套工具体系呈现出一个共同设计哲学——**"选项呈现"代替"自主决策"**。无论是第三方连接器（`suggest_connectors`）、深度研究（`suggest_research`）还是澄清提问（`ask_user_input_v0`），模型都被要求把"决定权"用 UI 控件的形式交还给用户，而不是替用户做选择或用文字征求同意（"Would you like me to...?"这类措辞在多处被明令禁止）。

## 6. "Claude in Claude"（Claudeception）与一处关键的文档内部矛盾

`<anthropic_api_in_artifacts>` 模块（第 1681–1881 行）说明 Artifacts 内可以直接 `fetch("https://api.anthropic.com/v1/messages")` 调用真实 Anthropic API 构建"AI 驱动的小程序"，且平台已代管 API Key。

**发现的内部不一致**：
- 第 1696 行示例代码硬编码 `model: "claude-sonnet-4-6", // Always use Sonnet 4.6`
- 第 1746 行 web_search 工具类型仍用旧版 `"web_search_20250305"`

而文档开头的产品信息模块（第 11 行）明确宣称"当前最新公开模型是 Fable 5 / Opus 5 / Sonnet 5 / Haiku 4.5"，`<search_instructions>` 模块里工具版本推断也应是较新的（技能参考资料里 Sonnet 4.6→Sonnet 5、web_search_20250305→web_search_20260209 都是已完成的版本升级）。

**这说明什么**：这个"Claude in Claude"子模块显然**没有跟着文档其他部分一起更新**，仍停留在 Sonnet 4.6 时代的写法。这是判断本文档性质的重要线索——它更像是**不同时间点捕获的真实系统提示词拼接/滚动更新而成**，而不是一次性、内部自洽编写的虚构文本：编写者/维护者更新了产品信息、模型矩阵、search 规则等"高频变动"区块，却遗漏了"Claude in Claude"这种低频触碰的子文档。

## 7. 版权合规与搜索规范：全文中最"工程化"的两个模块

- **版权合规**（1411–1482 行）是全文里规则最"数值化"的部分：15 词硬引用上限、单来源仅限一次引用、`{antml:cite}` 标签配合"内容必须改写，标签不是复现许可"的强调、以及一套"自查清单"（是否可以改写？是否超过15词？是否已经引用过这个来源？）。这套规则的精细度（例如"CNN eyewitnesses said it was 'mesmerizing' and a 'once in a lifetime experience'——即使各自不到15词，两句拼起来也算两次引用，上限是全局的"）与已公开验证过的真实 Claude.ai 版权条款高度一致，可信度较高。
- **搜索规范**（1355–1519 行）把"要不要搜索"归纳为一条清晰的经验法则："凡是关于当下状态（谁在任、价格、政策、是否还存在）的问题，即使 Claude 自认为确定答案，也要搜索验证"，并按任务复杂度给出 1/3–8/8–20/30+ 次调用的分级——这是一套相当成熟的"工具调用预算"设计，与技能参考资料里"Agent Design"章节的"效果优先于确定性调用次数"的理念一致。

## 8. 真实性评估（更新版）

结合本次读到的新证据（相较上一轮"整体分析"结论有实质性更新）：

**倾向"真实捕获"的证据**：
1. `{MEMORY_LISTING_ENTRY_REDACTED}`、`{LOCATION_REDACTED}` 这类**脱敏占位符**——虚构文档没有理由去"打码"一个不存在的用户数据。
2. `<profile>(not yet written)</profile>` —— 这与技能参考资料里 `<preferences_guardrails>` 一节描述的"listing 为空/`<profile>` 显示 not yet written 时该怎么办"的措辞**逐字吻合**，说明这是同一套真实产品机制的两处独立引用，而非拼凑。
3. 完整、格式规范、字段命名风格一致的 **30 个工具原始 JSON Schema**——这种级别的实现细节（如 `place_id` 大小写敏感提醒、`web_fetch` 的 `is_zdr`/`web_fetch_rate_limit_dark_launch` 这类内部灰度发布参数名）极难凭空杜撰，更像是真实系统的原始导出。
4. 当前日期"2026年7月24日星期五"与本次对话的系统日期（2026-07-25）仅差一天，符合"提示词捕获于对话前一天"的正常时间差。

**指向"存在编辑/推测成分"的证据**：
1. "Opus 5" 模型名不存在于官方目录（现实中最新是 Opus 4.8）。
2. Mythos/Glasswing 出口管制暂停复原的具体新闻时间线无法验证。
3. 第 6 节指出的"Claude in Claude"子模块明显滞后于文档其余部分的模型迭代。

**综合结论**：这份文档的**主体骨架、工具定义、隐私脱敏细节极可能来自一次或多次真实的 Claude.ai 系统提示词捕获**，具备很高的技术可信度；但"Opus 5"这一具体型号名称，以及围绕它的 Mythos/Glasswing 出口管制叙事，**在当前可验证的官方资料中找不到对应**——要么是编写/整理这份文档的人基于已知框架做了"面向未来"的推测性填充，要么是捕获自一次尚未公开、无法交叉验证的早期访问/内测环境。两者都不能排除，但"整份文档凭空虚构"这个假设，在看到完整工具列表和脱敏占位符后可信度明显降低。

## 9. 值得记录的设计模式（跨模块共性）

1. **"决策树优先于清单"**：可视化模块（Step0-3）、连接器建议流程（search→suggest→call）都采用"停在第一个匹配处"的显式决策树写法，而不是并列规则堆砌，减少模型误判的空间。
2. **"类别匹配 ≠ 风格偏好"这一区分反复出现**：无论是 MCP 工具选择（"那个工具做流程图但这个需求更有插画感"不构成跳过 MCP 的理由）还是版权引用（"去掉引号不算改写"），文档反复强调"表面上看起来合理的例外理由，其实是审美/风格偏好在伪装成真正的类别不匹配"，要求模型对这种自我合理化保持警惕。
3. **"不要暴露机制"是贯穿全文的写作风格**：memory 检索不提"我查了记忆"、visualizer 不提"我加载了 read_me"、连接器建议不提"按我的规则"——所有内部路由/工具调用逻辑都要求对用户"无感"，只有结果可见。
4. **"结尾即同意"模式**：`suggest_research`、`suggest_connectors` 等"渲染按钮"型工具都严格禁止在文字里用疑问句征求同意，理由是"按钮本身就是用户的同意入口，文字追问是重复且可能变成施压"。
5. **语气分级机制**：`visualize:show_widget` 的 loading 文案要求根据主题严肃程度切换"俏皮/无聊"两种模式，是全文里少见的、专门针对"次要 UI 文案"的情感基调规则，说明这套系统提示词的打磨颗粒度已经细到了加载动画文案这一层。

## 10. 结论

OPUS-5.md 是一份综合性的 Claude.ai 消费端系统提示词捕获/整理稿，覆盖身份定位、安全护栏、持久记忆、工具生态（30个工具）、内容安全（版权/图片/搜索）等所有主要子系统。文档的实现细节（脱敏占位符、工具 schema、内部灰度参数）具备很高的真实可信度，但其对"Opus 5"这一具体下一代模型名称的使用目前无法被现有官方资料验证，且文档内部存在明显的"版本滚动更新不彻底"的痕迹（Claude in Claude 子模块仍停留在 Sonnet 4.6/旧版 web_search）。总体而言，**这是一份"真实框架 + 部分推测性/未公开内容"的混合文档**，适合作为研究 Claude.ai 系统提示词工程范式的参考，但其中具体的模型代号、定价、时间线声明不应被当作已确认的官方事实。
