- **分析日期**：2026-07-25
- **文档定位**：本文件**完全独立成篇**，是对用户自己这套设计的落地展开，不是对 `OPUS-5.md` 或此前 MongoDB+ADK 迁移分析的修改或延续——虽然会在合适的地方复用此前已验证过的原则（如"对话中随时写，不等到最后"、str_replace 语义、乐观锁思路），但整体架构是围绕用户这次给出的规格重新设计的。

## 1. 设计目标与总览

这套系统要解决的核心问题：让一个基于 Google ADK 的 agent 拥有**跨会话的结构化长期记忆**，同时满足几条明确的约束——不用向量检索、单集合存储、身份类数据不落库（永远读取权威信源）、记忆按"类型"而非"文件"组织、读写规则区分"程序强制执行"和"LLM 自主决定"两层。

整体数据流：

```text
用户信息系统 ──(每次激活实时读取)──> session.state ──(instruction 模板)──> LLM 看到
                                        ▲
MongoDB (agent_memories) ──(激活时 hydrate)──┘
                                        │
                              会话过程中读写操作
                                        │
                        (会话/任务结束时 flush-back)
                                        ▼
                                    MongoDB
```

五类记忆里，只有"身份与组织记忆"完全不进入这个 MongoDB 读写缓存循环——它是每次都从外部权威系统实时拉取的引用数据，不是"被记住"的东西。

## 2. 记忆类型定义

| 类型 | 内容 | 是否存 MongoDB |
| --- | --- | --- |
| **身份与组织记忆**（profile） | 姓名、部门、公司、常用办公地/时区 | **否**——每次从用户信息系统（HRIS/目录服务/IdP 等）实时读取，agent 从不"记住"它，只是"引用"它 |
| **情景记忆**（episodic） | 具体的过去事件和交互经历（"用户上周问过 X""上次生成的报表用了 Y 口径"） | 是 |
| **业务话题和领域记忆**（topics/domain） | 用户反复咨询的业务领域、常见困惑点、岗位/行业术语习惯 | 是 |
| **用户偏好记忆**（preferences） | 输出格式（Excel/PPT/纯文本）、详略程度、语气、敏感操作是否需要人工确认 | 是 |
| **进行中事务记忆**（long-run task） | 正在推进的事——多步任务的当前进度、下一步该做什么 | 是 |

身份记忆之所以单列且不落库，是因为它是**权威数据**（authoritative data）而非**观察/陈述积累出来的记忆**——组织架构随时可能变（调岗、改名），把它缓存在 Mongo 里会引入"过期身份信息"的风险，而这类数据本身通常有一个更权威的信源（HR 系统/目录服务），实时读取的成本远低于维护一份缓存并处理失效问题的成本。

---

## 3. 记忆的三类标签

| 标签 | 含义 | 典型来源 |
| --- | --- | --- |
| `[confirmed]` | 用户明确说过的话，或者 real data（权威系统给出的既定事实） | 身份与组织记忆（虽然它不落库，但如果偶尔以文本形式出现在其他记忆的引用中，用这个标签）、用户明确陈述的偏好 |
| `[observed]` | 由 agent 观察得出，不是用户直接说的，而是从行为/工具调用中推断出的状态 | 进行中事务记忆（比如从一系列工具调用推断出"用户正在准备季度报告，已完成数据拉取，卡在图表环节"） |
| `[inferred]` | 模型自己的推论 | 业务话题/领域记忆里"这个用户似乎经常混淆预扣税和申报周期"这类归纳性判断；也可能出现在情景记忆的总结性条目里 |

三个标签的信任等级依次递减：`[confirmed]` 是可以直接当事实使用的；`[observed]` 是行为层面的推断，展示时要注意别把"agent 观察到的"和"用户确认过的"混为一谈；`[inferred]` 是最弱的一层，属于"值得关注但不该当作定论"的模式识别结果，应用这类记忆时要格外谨慎，避免把一次性的模式识别固化成对用户的刻板印象。

标签是打在**每一条记忆记录**上的，不是绑定在"类型"上——同一个类型（比如 long-run task）里完全可以同时存在 `[observed]` 的自动推断条目和 `[confirmed]` 的用户明确确认条目（例如用户说"对，这个任务我们先暂停"，这条应该记成 `[confirmed]`，而不是继续用 `[observed]`）。

身份记忆因为压根不落库，天然不参与这套标签体系。

## 4. 存储架构：MongoDB 单集合 + Session State 读写缓存模式

### 4.1 关键架构选择：Mongo 是权威存储，session.state 是会话内的工作副本

这套设计和"每次操作都直接读写 Mongo"的同步模式不同，而是一个**读穿透 + 写回（read-through / write-back）缓存模式**：

- **激活（hydrate）**：agent 激活时，从 MongoDB 把该用户的长期记忆（preferences、long_run_task，按第6节的固定/动态规则决定是否含 episodic/topics）读出来，写入 `session.state`。
- **会话期间**：六个记忆操作函数在会话过程中主要针对 `session.state` 里的工作副本读写，不需要每次调用都单独打一次 Mongo（这一步几乎零成本，此前分析已确认 `session.state` 本身只是应用侧字典）。
- **结束（flush-back）**：agent 结束任务（会话结束）时，把 `session.state` 里累积的变更写回 MongoDB。

这个模式的好处是会话内读写快、不依赖 Mongo 可用性做每一步；**代价是有持久性风险**——如果会话异常中断（连接断开、进程崩溃）而没有走到"结束"这一步，本次会话里新增的记忆可能丢失。这一点在第7.3节详细展开，并给出缓解建议。

### 4.2 集合 Schema 草案

**单一集合**，每个 `(user_id, type)` 组合对应一个文档（不是每条记忆一个文档，而是每个类型一个文档，文档内部是持续增长的正文）：

```javascript
db.createCollection("agent_memories", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["user_id", "type", "body", "updated_at"],
      properties: {
        user_id: {
          bsonType: "string",
          description: "多租户分区键，所有查询/写入必须带这个过滤条件"
        },
        type: {
          enum: ["episodic", "topics", "preferences", "long_run_task"],
          description: "四种落库的记忆类型；profile 不在此列，因为它从不落库"
        },
        body: {
          bsonType: "string",
          description: "按行拆分、每行打标签的正文，例如 '[observed] 2026-07-25T09:12Z 用户开始准备Q2区域销售对比分析'"
        },
        size_bytes: {
          bsonType: "int",
          description: "body 的字节数缓存，用于快速判断是否触发裁剪，避免每次都重新计算"
        },
        version: {
          bsonType: "int",
          description: "内部乐观锁版本号，仅供 flush-back / 内部实现使用，不暴露在六个函数的对外签名里"
        },
        status: {
          enum: ["active", "archived"],
          description: "4.4节衰减机制用的状态位：active 参与正常的固定/动态读取；archived 表示被巡检任务判定为待复核/疑似废弃，暂不进入固定读取或 load_all_memory 的默认返回，需显式确认后才恢复为 active 或彻底删除"
        },
        created_at: { bsonType: "date" },
        updated_at: { bsonType: "date" }
      }
    }
  }
});

db.agent_memories.createIndex({ user_id: 1, type: 1 }, { unique: true });
```

四种类型、每用户最多四个文档——这是"单一集合"的自然落地方式：不需要像"每个 topic 一个文件"那样按子话题再拆分文档，`topics`/`episodic` 内部的多条具体内容都作为**同一个文档正文里的多行**存在，用标签+时间戳区分，而不是拆成多个文档。

### 4.3 大小上限与旧记忆清理策略

- **软上限**：每个 `(user_id, type)` 文档的 `body` 建议控制在 **200,000 字符以内**，远低于 MongoDB 单文档 16MB 的硬限制，留出充分余量。
- **触发时机**：`append_memory`、`write_memory`、`replace_memory` 写入后，如果 `body` 超过软上限，触发清理。
- **默认清理策略：先进先出（FIFO）**——按行（每行是一条独立的打标签记忆）从最旧的开始删除，直到 `body` 重新落到软上限以内。这是最简单、可预测的默认策略。
- **可选优化（按类型差异化）**：
  - `episodic`（情景记忆）：除了 FIFO，建议**额外**加一条基于时间的过期规则（例如超过 N 天的事件即便没触发大小上限也定期清理）——情景记忆的时效性通常比领域知识衰减得快。
  - `topics`（业务话题/领域记忆）：FIFO 可能会误删仍然有效的领域知识（比如"用户经常问 VAT"这种模式即使很久没提也可能仍然成立）。更稳妥的做法是清理前**先做一次去重/合并**（同一话题的多条记录合并成一条更新过的记录），而不是简单按时间顺序丢弃最旧的——这是一个值得后续迭代的优化点，初版可以先用 FIFO，观察实际数据分布后再决定是否需要合并逻辑。
  - `preferences`：一般不会无限增长（偏好项数量有限），触发清理的情况应该很少见；如果触发了，更可能说明该定期做一次"偏好合并/去重"而不是简单丢弃。
  - `long_run_task`：已完成的任务条目应该在任务结束时就被显式清理（见6.2/6.4），而不是等到触发大小上限才清理——这类记忆的生命周期通常和"任务是否还在进行"绑定，而不是和"占用空间是否超标"绑定。

上面这些都是**被动触发**的清理（只在写入导致超限时才发生）。但很多记忆会"从此再也没人碰过"——从未触发大小上限，内容却早已过期失效。这需要独立于写入事件的**主动衰减机制**，见4.4。

### 4.4 各类型记忆的衰减/过期机制

4.3 处理的是"写入时超限才清理"；这一节处理的是"即使从不超限，记忆本身的有效性也会随时间/使用情况变化"——这是两套互补的机制：4.3 由**写入事件**触发，4.4 里的大部分规则需要一个**独立于会话生命周期的定期巡检任务**触发（见4.4.7），因为很多该衰减的记忆恰恰是"很久没人写入也没人读取"的那些。

#### 4.4.0 跨类型的共同原则

- **衰减不等于物理删除**：合理的"到期动作"可以是降低检索优先级、合并归档、标记待人工/LLM复核，未必是直接删除。只有明确判定"已经彻底无效"的内容才适合硬删除。
- **标签决定衰减速度**：置信等级从高到低是 `[confirmed]` > `[observed]` > `[inferred]`；同样的大小/时间压力下，应该优先淘汰 `[inferred]` 的行，其次是 `[observed]`，最后才轮到 `[confirmed]`——4.3 里"纯 FIFO"的默认策略可以升级为"**按 (标签置信度, 时间) 的二级排序**"来决定淘汰顺序，而不是单纯按时间。
- **类型之间存在"晋升/归档"的生命周期关系**，而不是各自孤立衰减（详见下文各小节）：`long_run_task` 完成/过期后晋升为一条 `episodic` 记录；`episodic` 里反复出现的模式经归纳后晋升为 `topics` 条目。这个链条本质上是在模拟"具体事件 → 历史记录 → 归纳出的语义知识"这一自然的记忆固化过程。

#### 4.4.1 身份与组织记忆（profile）：不适用"衰减"，只有"会话内缓存新鲜度"问题

因为这类记忆从不落库、每次都从权威系统实时读取，所以严格意义上不存在"过期"问题——它永远是最新的。唯一需要考虑的是**会话内缓存的有效期**：如果 `before_agent_callback` 只在会话开始时拉取一次，而会话本身持续很久（长任务、长对话），中途该数据在权威系统里发生了变化怎么办？建议：设置一个较短的会话内缓存 TTL（例如 15–30 分钟），超过这个时长后下一次工具调用/回合自动重新拉取一次，而不是整个会话期间只信一次快照。这不是"记忆衰减"，只是缓存失效策略，但值得和其余四类的衰减机制放在一起统一考虑，避免遗漏。

#### 4.4.2 情景记忆（episodic）：衰减机制最经典的一类

- **按标签差异化的硬 TTL**：默认建议 `[observed]`/`[inferred]` 类事件 **180 天**未被强化即视为过期物理删除；`[confirmed]` 类事件（用户明确确认/陈述过的重大事项）默认**不设硬 TTL**，只受4.3的大小上限约束——这类事件的"被记住"本身就是用户明确认可过的，不应该单纯因为时间久了就自动抹去。
- **访问强化（reinforcement）**：如果某条情景记忆被 `load_memory('episodic')` 取出并在对话中被引用/确认（例如用户回应"对，就是那次"），应当刷新它的时间戳（类似 LRU 缓存的"最近访问"语义），而不是任由创建时间不断老化——被重复提及的事件说明它仍然重要。
- **晋升为 topics**：如果同一类情景事件在一段时间内反复出现（比如"用户又一次问了同样的报表口径问题"，累计达到一个阈值，如 3 次），应该把这个重复模式**归纳成一条 `topics` 记忆**（"用户经常对XX口径感到困惑"），原本的多条零散情景记录可以随后按 TTL 正常衰减掉——具体的事件不需要一直留着，但它揭示的模式应该被保留下来。这个归纳判断可以是巡检任务里的一条规则，也可以设计成 LLM 在 `after_model_callback` 里可选触发的一次总结性写入。

#### 4.4.3 业务话题/领域记忆（topics/domain）：按"停止被强化"衰减，而不是按时间

- **不设硬 TTL**——纯按创建时间删除会误伤仍然成立、只是最近没被提起的领域知识。
- **衰减信号是"disuse"（多久没被重新验证/引用），而不是"age"（多久前创建）**：建议默认阈值——一条 topics 记录如果 **12 个月**内既没有被新的情景事件强化，也没有被 `load_memory('topics')` 命中并在对话中被确认，就标记为"待复核"（不是直接删除），下次相关会话里可以让 LLM 或人工确认它是否依然成立。
- **角色变化作为强触发信号**：由于 `profile`（身份与组织记忆）是每次都实时读取的权威数据，可以在 `before_agent_callback` 里比较"这次读到的部门/岗位"和"上一次记录的部门/岗位"是否发生变化——一旦检测到用户换了部门/岗位，这是一个明确信号，说明其现有的 topics 记忆很可能大部分已经不适用，应该主动触发一次全量复核（而不是等 12 个月的默认阈值慢慢过期）。
- **合并优于删除**：复核时优先做"同类条目合并去重、更新时间戳"，而不是简单丢弃——参考4.3里已经提到的合并策略，这里进一步明确合并本身也是一种"衰减处理方式"，不是必须以删除收尾。

#### 4.4.4 用户偏好记忆（preferences）：衰减方式是"被新陈述覆盖"，不是时间

- **原则上不设 TTL**——用户几个月不提偏好设置，不代表偏好本身失效，这类记忆的默认假设应该是"持续有效直到被显式改变"。
- **唯一正当的"过期"方式是被覆盖（supersession）**：用户表达新偏好时，用 `replace_memory` 替换旧的对应行，而不是单纯 `append` 追加——旧偏好的"过期"发生在这次替换的瞬间，不是随时间推移。
- **需要防范的问题是"追加式误写"导致的重复/冲突条目共存**（例如 LLM 该用 `replace_memory` 却用了 `append_memory`，导致"偏好Excel"和"偏好PPT"两条同时存在）——建议在 flush-back 或巡检任务里加一道**一致性检查**：同一维度（输出格式/详略程度/语气/敏感操作确认）如果出现多条冲突记录，只保留时间戳最新的一条，其余的按"被覆盖"处理清理掉。这本质上是一种事后校正，弥补动态写入规则里 LLM 可能选错函数的风险。

#### 4.4.5 进行中事务记忆（long_run_task）：衰减机制和任务生命周期绑定

- **主触发——任务完成/取消**：`after_tool_callback` 检测到任务完成信号（或 LLM/用户显式确认完成）时，**立即**清除该任务对应的行（`replace_memory` 为空字符串），不等待任何 TTL——这是最主要、最及时的过期路径，已经在6.2/6.4提到过。
- **副触发——长期无活动的"僵尸任务"TTL**：如果一个任务被记录为"进行中"，但连续一段时间（建议默认 **14–30 天**）都没有相关的工具调用或对话提及，很可能是用户已经放弃或通过其他渠道完成了、只是没告诉 agent。这类任务不应该无限期占用"固定读取"的上下文位置，也不该悄悄删除（用户可能只是暂停了，还想回来继续）——建议的处理是**归档而非删除**：把它从"活跃的 long_run_task"里移出，同时在下一次相关交互中（比如用户提到相关关键词，或只是简单地在下次会话开场）by LLM 主动确认一句"你之前在推进的 XX 是否还需要继续？"，得到回应后再决定是彻底清除还是恢复为活跃任务。
- **晋升为 episodic**：任务无论是正常完成、被取消，还是被判定为"僵尸任务"归档，都应该在结束时生成一条对应的 `episodic` 记录（"用户在 [时间] 推进过 XX 任务，最终 [完成/取消/无声放弃]"）——这样任务本身的"活跃状态"记忆消失了，但"这件事发生过"这个历史事实被保留进了情景记忆里，遵循4.4.0提到的"晋升"生命周期，而不是任务一结束就彻底什么记录都不剩。

#### 4.4.6 汇总表

| 记忆类型 | 衰减触发方式 | 默认参数建议 | 到期后动作 |
| --- | --- | --- | --- |
| profile | 不适用（不落库）；仅会话内缓存新鲜度 | 会话开始必刷新；长会话建议每 15–30 分钟重新拉取一次 | 重新实时拉取，覆盖旧值 |
| episodic | 时间 TTL（按标签差异化）+ 访问强化重置 + 4.3 的大小裁剪 | `[confirmed]` 不设硬 TTL；`[observed]`/`[inferred]` 默认 180 天 | 到期物理删除；被引用/确认则刷新时间戳；同类事件反复出现达到阈值则晋升为 topics 条目 |
| topics | 停止被强化（disuse）+ 角色变化强触发 | 12 个月无强化标记待复核；`profile` 部门/岗位变化时立即触发复核 | 复核后合并去重、更新时间戳，或标记为待确认；不做无条件物理删除 |
| preferences | 被新陈述覆盖（supersession），非时间驱动 | 不设 TTL | 被 `replace_memory` 替换；巡检/flush-back 时做冲突检测与去重 |
| long_run_task | 任务完成/取消（主，立即触发）+ 长期无活动 TTL（副） | 无活动 14–30 天视为疑似废弃 | 完成/取消：立即清除并晋升为 episodic 记录；疑似废弃：归档，下次相关交互向用户确认 |

#### 4.4.7 需要一个独立的定期巡检任务（scheduled sweep）

4.3 的清理只在"写入触发导致超限"时运行；但本节大部分衰减规则（episodic 的时间 TTL、topics 的 disuse 判定、long_run_task 的僵尸任务检测）需要在**没有任何新写入**的情况下也能被发现和处理——这意味着仅靠"六个函数在被调用时顺带检查"是覆盖不到的，必须有一个独立于单次会话生命周期的后台任务（例如每天运行一次），职责包括：

1. 扫描 `episodic` 文档，按行内标签+时间戳判断是否超过对应 TTL，执行删除或晋升为 `topics`。
2. 扫描 `topics` 文档，标记超过 disuse 阈值的条目为待复核；同时对比每个用户最近一次 `before_agent_callback` 记录的部门/岗位快照与巡检时刻权威系统的当前值，检测角色变化并触发全量复核。
3. 扫描 `long_run_task` 文档，检测无活动超过阈值的任务，执行归档 + 生成对应 `episodic` 记录。
4. （可选）对 `preferences` 做一致性检查，清理因误用 `append_memory` 造成的重复/冲突条目。

这个巡检任务和第7.3节的 flush-back 是两套独立机制，职责不同：**flush-back 处理"这次会话新产生的内容如何落盘"**，**巡检任务处理"库里已经落盘、但长期没有新的读写事件去自然触发老化"的内容**。两者都需要，缺一不可——只有 flush-back 没有巡检任务，衰减规则形同虚设；只有巡检任务没有 flush-back，会话产生的新记忆根本进不了库。

## 5. 记忆操作函数（六个 functions）

这六个函数是 agent 侧（ADK `FunctionTool`）暴露给 LLM 的记忆操作接口，运行时主要作用于 `session.state` 里的工作副本（第4.1节的缓存模式）：

| 函数 | 作用 | 关键行为 |
| --- | --- | --- |
| `load_all_memory()` | 读取该用户**全部**类型的记忆，加入上下文 | 从 `session.state` 里取出 episodic/topics/preferences/long_run_task 四类的完整正文拼接返回；调用本身作为工具结果自然进入对话，不需要额外的 instruction 模板处理 |
| `load_memory(type)` | 按类型读取一部分记忆，加入上下文 | 同上，但只取指定 `type` 的正文；`type` 取值限定在四个落库类型（不含 profile——profile 从不通过这个接口读取，见第6.1节） |
| `write_memory(type, content)` | 整篇覆盖某类型的记忆正文 | 对应 OPUS 系设计里的"全量重写"语义：传入的 `content` 替换整个 `body`；覆盖前建议做一次大小校验（超过软上限直接拒绝，要求调用方精简后重试，而不是静默截断） |
| `replace_memory(type, old_str, new_str)` | 对某类型正文做局部替换 | `old_str` 必须在该类型正文里唯一匹配，`new_str` 留空即表示"删除这一小段"（复用 OPUS 设计里验证过的这条约定：不需要单独设计一个"删除单条记忆"的函数，`replace_memory(type, old_str, "")` 就能覆盖这个需求） |
| `append_memory(type, content)` | 在某类型正文末尾追加一条新记忆 | 新增内容会自动带上时间戳前缀（便于情景记忆按时间排序/清理）；写入后检查是否超过软上限，触发第4.3节的清理逻辑 |
| `delete_all_memory()` | 删除该用户全部落库记忆 | 高风险操作，建议**只在用户明确要求"忘记我的一切"时**才调用，且调用前要求 agent 向用户做一次确认（复用此前分析验证过的保守删除原则：不要主动清理，只在用户明确要求时执行） |
| `delete_memory(type)` | 删除某一类型的全部记忆 | 同样建议先向用户确认，尤其是删除 `preferences` 或 `long_run_task` 这种会直接影响后续交互体验的类型 |

**内部实现细节（不暴露在函数签名里，但实现时应该考虑）**：

- 会话内的读写默认只作用于 `session.state`；实际落 Mongo 的时机由第7.3节的 flush-back 机制统一处理，六个函数本身不需要每次都单独往返 Mongo（除非你决定采用"边写边同步"的更保守策略，见7.3的风险权衡）。
- 尽管对外函数签名里没有 `if_version` 这类并发令牌（这是用户明确给出的规格，保持简单），**flush-back 写回 Mongo 时内部仍然建议使用乐观锁**（`version` 字段），原因见第8节"并发与一致性考虑"。

## 6. 混合式记忆读写规则

固定规则由程序代码强制执行，不依赖 LLM 判断；动态规则的"什么时候执行"由 system prompt 里的指令引导 LLM 自主决定何时调用相应工具。

### 6.1 固定读取规则

**每一次 agent 激活时**，程序强制读取以下三类，放入上下文，不需要 LLM 主动请求（为了更好的开箱体验——用户不需要先问"你还记得我的偏好吗"才能让 agent 表现正确）：

1. **身份与组织记忆**——不经过 Mongo，直接实时查询用户信息系统。
2. **用户偏好记忆**——从 `session.state`（已在会话开始时从 Mongo hydrate 过）读出全文。
3. **进行中事务记忆**——同上，从 `session.state` 读出全文。

**技术实现**：这三类内容通过 `before_agent_callback` 写入 `session.state`（例如 `state['profile_text']`、`state['preferences_text']`、`state['long_run_task_text']`），并且——这一点是此前 ADK 澄清分析里强调过、必须再次落实的——**光写进 `session.state` 不够，还要在 agent 的 `instruction` 字符串里用 `{profile_text}`、`{preferences_text}`、`{long_run_task_text}` 占位符显式引用它们**，框架才会在每次调用模型前把这些内容替换进真正发给模型的 prompt。如果这几类内容可能包含字面花括号（不太常见，但比如偏好里存了一段 JSON 格式偏好），改用 `InstructionProvider` + `inject_session_state()` 手动拼接。

### 6.2 固定写入规则

1. **身份与组织记忆刷新**：每次 agent 激活时，从用户信息系统读取最新数据，写入 `session.state`（**不写入 Mongo**，因为这类数据本来就不落库）。是否每次"激活"都等同于每一个用户回合都重新拉取，还是只在会话开始时拉取一次，是一个需要权衡的点（见第9节），建议至少在会话开始时拉取一次，若该信息系统调用成本较低，也可以每回合刷新以处理"会话进行中用户身份信息发生变化"的边缘情况。
2. **进行中事务记忆更新**：使用 `after_tool_callback()`——每次工具调用结束后，检查这次工具调用是否代表某个进行中任务的进展（例如调用了"生成报表""发送邮件""安排会议"这类和多步任务相关的工具），如果是，则确定性地（不依赖 LLM 判断）更新 `session.state` 里的 long_run_task 工作副本：新任务用 `append`，已有任务进度更新用 `replace`（按 old_str/new_str 定位到具体任务行），任务完成时应清理掉对应行（`replace` 成空字符串）而不是等到下次大小超限才清理。

### 6.3 动态读取规则

**情景记忆**和**业务话题/领域记忆**不做固定加载，而是根据用户当前这一轮的意图，由 LLM 自主判断是否需要调用 `load_memory('episodic')`、`load_memory('topics')` 或 `load_all_memory()`。system prompt 里需要给出判断依据的指引，例如："当用户的问题涉及'我们之前聊过的''上次那个''老问题'这类指向历史的措辞时，先调用 load_memory 或 load_all_memory 再回答；不要在没有历史线索的通用问题上调用这些工具。"

因为这套设计只有四个落库类型（不像 OPUS-5.md 原设计那样有开放数量的按 slug 分文件），这里甚至不需要 OPUS-5.md 里那套"listing 目录 + 判断相关性"的中间层——LLM 只需要知道"有 episodic 和 topics 这两个可按需读取的类型"，直接按类型调用即可，省掉了一层间接性。这是相对 OPUS-5.md 原设计的一个合理简化，而不是能力缩水（前提是类型数量确实保持在个位数，不会像 OPUS-5.md 的 per-topic 文件那样无限增长）。

### 6.4 动态写入规则

核心原则复用 OPUS-5.md 分析中验证过的表述——**"Write during the conversation, not at the end — and without being asked"**：情景记忆和业务话题/领域记忆的写入不等到会话结束才汇总，而是在对话进行中，LLM 一旦判断某条信息值得记录，就立刻调用 `append_memory`/`replace_memory`/`write_memory`。

**技术挂载点**：`after_model_callback`（ADK 里这个回调的规范名称是 `after_model_callback`；"after_llm_callback" 是同一个挂载点的口语化叫法，落地实现时请以 ADK 文档里的 `after_model_callback` 为准）。需要明确一点：**这个回调本身不是"决定写什么"的地方**——决定写什么、什么时候写，是 LLM 根据 system prompt 里的动态规则指引自主判断后，通过显式调用 `append_memory` 等工具来完成的（这本身就是标准的 ADK 工具调用流程，工具调用结果自然进入对话，不需要额外的 state/instruction 模板处理）。`after_model_callback` 在这里的作用是**技术兜底**：
- 确认本轮 LLM 是否触发了记忆写入类工具调用，做日志/可观测性记录；
- 标记 `session.state` 为"有未落库的变更"，供 flush-back 步骤（第7.3节）判断是否需要写回；
- （可选）作为安全网，用一个更轻量的辅助判断（规则或小模型）扫一遍这轮对话，检查是否有明显该记但 LLM 没有主动调用工具去记的内容——这一层是可选的增强，不是核心机制，核心机制仍然是 LLM 自主调用工具。

### 6.5 规则矩阵总表

| 记忆类型 | 落 MongoDB？ | 固定读取 | 固定写入 | 动态读取（LLM 工具） | 动态写入（LLM 工具 / 回调） |
| --- | --- | --- | --- | --- | --- |
| 身份与组织（profile） | 否 | 是，每次激活 | 是，`before_agent_callback` 实时拉取用户信息系统 | 否 | 否——本质只读引用数据，agent 不应"记住"或改写它 |
| 用户偏好（preferences） | 是 | 是，每次激活 | 无固定写入；变更走动态规则 | 可选（`load_memory('preferences')` 用于确认当前设置） | 是，用户明确表达偏好变化时，LLM 调用 `write/replace/append_memory` |
| 进行中事务（long_run_task） | 是 | 是，每次激活 | 是，`after_tool_callback()` 自动更新进度 | 可选 | 也可由 LLM 主动调用（例如任务完成时显式确认并清理） |
| 情景记忆（episodic） | 是 | 否 | 否 | 是，LLM 按用户意图判断调用 | 是，LLM 在对话中随时调用 `append_memory`，`after_model_callback` 做技术兜底 |
| 业务话题/领域（topics） | 是 | 否 | 否 | 是，同上 | 是，同上 |

## 7. 与 Google ADK 的对接细节

### 7.1 `session.state` 可见性问题的处理

复用此前分析已经核实过的结论：LLM 无法直接看到 `session.state`，它是应用侧的字典，只有通过 **instruction 模板的 `{key}` 占位符**（或 `InstructionProvider` + `inject_session_state()`）才能进入模型实际看到的 prompt；而通过 `FunctionTool` 调用返回的内容（`load_memory`/`load_all_memory` 这类）会作为工具结果自然进入对话上下文，不需要额外的模板处理。这个区分决定了：

- **固定读取的三类**（profile/preferences/long_run_task）必须走"state + instruction 模板"这条路径，因为它们要求"不需要 LLM 主动请求就能看到"。
- **动态读取的两类**（episodic/topics）走"FunctionTool 调用结果"这条路径，因为它们本来就设计成"LLM 判断后主动请求"。

### 7.2 各回调的职责划分

| ADK 回调 | 职责 |
| --- | --- |
| `before_agent_callback` | 激活时/每回合开始时：(a) 实时拉取用户信息系统写入 `state['profile_text']`；(b) 若本次是会话内首次调用，从 MongoDB hydrate preferences/long_run_task 写入对应 state key |
| `after_tool_callback` | 每次工具调用结束后：判断是否与进行中任务相关，确定性地更新 `state` 里的 long_run_task 工作副本 |
| `after_model_callback`（用户所指的 "after_llm_callback"） | 每轮 LLM 响应后：记录本轮是否有记忆写入类工具调用被触发；标记 state 是否"dirty"；可选的安全网扫描 |
| （会话结束钩子，具体挂载点取决于你的应用如何定义"会话结束"） | flush-back：把 `session.state` 里 preferences/long_run_task/episodic/topics 四类的最终内容写回 MongoDB（见7.3） |

### 7.3 Hydrate / Flush-back 的具体机制与风险

**Hydrate（激活时读取）**：会话开始时，用 `user_id` 查询 `agent_memories` 集合里的 `preferences`/`long_run_task` 两个文档（这两类是固定读取的），读出 `body` 写入 `session.state`。`episodic`/`topics` 不在激活时主动 hydrate 全文——但如果你希望"LLM 调用 `load_memory('episodic')` 时不需要再打一次 Mongo"，可以选择在激活时把这两类也一并 hydrate 进 state（反正写进 state 本身几乎零成本，见此前分析），只是不把它们模板进 instruction。**建议采用这个做法**：四类落库记忆在激活时全部 hydrate 进 `session.state`，只是 instruction 模板只引用其中两类（preferences/long_run_task），episodic/topics 留给 `FunctionTool` 调用时从 state 里现取。这样"读 Mongo"这个动作全程只发生一次（会话开始时），后续无论是固定读取还是动态读取都只是读内存里的 state，不需要额外的数据库往返。

**Flush-back（结束时写回）的风险**：这是这套设计里**唯一值得重点提醒的架构风险**——"只在会话结束时才写回 Mongo"意味着如果会话异常中断（网络断开、进程崩溃、用户直接关闭页面而没有触发"结束"信号），**本次会话里通过 `append_memory`/`replace_memory` 新增的记忆会丢失**，因为它们只存在于 `session.state` 里，从未落过盘。

建议的缓解方案（二选一或组合使用）：

1. **接受风险，只做最终 flush**：如果你的应用场景里"会话"通常有明确的结束信号（比如显式的"任务完成"操作、固定的会话超时清理逻辑一定会触发），且偶尔丢失一两条情景记忆的代价可以接受，那么保持"只在结束时 flush"是可以接受的简单方案。
2. **增量安全网 flush**（推荐）：不改变"主要在 state 里工作"的模式，但在 `after_tool_callback`（long_run_task 更新后）和 `after_model_callback`（检测到本轮有记忆写入类工具调用后）**顺带做一次轻量的增量写回**——只把这一轮新增/变更的部分（而不是整个 body）追加/更新到 Mongo，代价很低（一次 `findOneAndUpdate` 的 `$set`/字符串拼接），但把"最坏情况丢失的数据量"从"整个会话"降低到"最后一个回合"。这是更稳健的做法，建议作为默认实现。

无论选哪种，**flush-back 时都不建议做"整篇覆盖"式的写回**（即不要用 `session.state` 里的内容直接 `write_memory` 式地覆盖 Mongo 里已有的 `body`）——理由见第8节。

## 8. 并发与一致性考虑

- **多会话并发风险**：如果同一用户可能同时存在多个 agent 会话（多个浏览器标签页、多个渠道），且都在同一时间段结束并触发 flush-back，"整篇覆盖"式的写回会导致后结束的会话覆盖掉先结束会话新增的内容，造成数据丢失。**建议 flush-back 使用"增量追加"而不是"整篇覆盖"**——即只把本次会话新增的行 `$push`/拼接到 Mongo 现有的 `body` 后面，而不是拿 `session.state` 里 hydrate 时的旧内容 + 本次新增内容拼成一个完整字符串再整体覆盖（后者会连带覆盖掉 hydrate 之后、flush 之前，由其他并发会话写入的内容）。
- **内部乐观锁**：虽然六个函数的对外签名里没有版本令牌，flush-back 的内部实现建议仍然使用第4.2节 schema 里的 `version` 字段——写回前先读一次当前 `version`，用 `findOneAndUpdate({user_id, type, version: expected}, {$set:..., $inc:{version:1}})` 做原子更新；版本不匹配时说明有并发写入，走"追加而不是覆盖"的合并逻辑重试。这一层对 LLM 和六个函数的调用方完全透明，只是内部实现细节。
- **删除操作的并发语义**：`delete_all_memory()`/`delete_memory(type)` 是破坏性操作，执行前除了第5节建议的"向用户确认"，实现上也应该直接对 Mongo 做删除（不要只清空 `session.state` 然后指望 flush-back 去同步删除——删除应该是立即生效的操作，不应该走缓存写回的异步路径，否则会话异常中断时"用户以为删除了但其实没删掉"的体验非常糟糕）。

## 9. 需要你确认/决策的开放问题

- **身份信息刷新粒度**：`before_agent_callback` 实时拉取用户信息系统，是打算"每次用户发一轮消息就拉一次"还是"只在会话开始时拉一次"？前者更实时但增加每轮延迟和外部系统调用量，后者更省成本但没法处理会话中途身份变化的边缘情况（这种情况在实践中通常很罕见，可以接受）。
- **"会话结束"具体如何定义**：flush-back 挂在哪个事件上，取决于你的应用怎么界定"agent 结束任务"——是用户显式的"结束对话"操作、一段时间无交互的超时判定，还是某个业务层面"任务已完成"的信号？这决定了 flush-back 钩子具体挂在 ADK 的哪个生命周期事件上，以及是否需要额外实现一个显式的会话终止检测逻辑。
- **是否采纳"增量安全网 flush"**：第7.3节给出的两个方案里，是接受"只在结束时 flush"的丢失风险，还是采用增量安全网写回？这直接影响 `after_tool_callback`/`after_model_callback` 的实现复杂度。
- **topics/domain 记忆的清理策略**：第4.3/4.4节提到 FIFO 对领域知识类记忆可能不是最优策略（可能需要去重/合并而不是简单丢弃），初版用 FIFO 简化实现，但建议观察实际数据积累情况后再决定是否要引入合并逻辑。
- **`after_model_callback` 里的"安全网扫描"是否需要**：这是一个可选的增强层（用规则或小模型补充检测 LLM 遗漏的记忆点），增加系统复杂度和额外的模型调用成本，需要你根据"遗漏率"的实际严重程度决定是否值得做。
- **多渠道/多会话并发的实际发生概率**：如果你的产品形态基本不会出现同一用户同时开多个会话的情况，第8节的并发处理可以简化（比如直接用整篇覆盖也没问题）；如果确实存在，第8节的"增量追加+乐观锁"就不是可选项而是必须项。
- **4.4节各项 TTL/阈值的具体取值**：180天、12个月、14–30天这些都是建议性默认值，不是从你的业务数据推导出来的——需要结合实际用户行为（多久算"话题过时"、多久算"任务疑似废弃"）来调优，初版可以先上线保守的默认值，再根据观察到的误删/误留情况调整。
- **是否已有可用的定期任务/调度基础设施**：4.4.7 提出的巡检任务需要脱离单次会话生命周期独立运行（例如 cron job、消息队列的延迟任务，或云厂商的 scheduled function），这依赖你现有的技术栈里是否已经有类似的调度能力，还是需要新引入一套。
- **"archived"状态的具体交互设计**：4.2节 schema 已加入 `status: active|archived` 字段承接4.4节的归档需求，但"什么时候、以什么措辞向用户确认一条 archived 的记忆是否要恢复"这类交互细节还没有设计，需要结合具体产品体验来定。

## 10. 建议的最小可行实现顺序

1. **先跑通 hydrate → instruction 模板这条链路**：只做 preferences，`before_agent_callback` 从 Mongo 读一个假文档写进 state，instruction 模板用 `{preferences_text}` 引用，验证"Mongo → state → 模型真正看到"整条链路。
2. **接入身份信息系统**：`before_agent_callback` 增加实时拉取（先接一个 mock/测试用的用户信息系统），确认这类"不落库、纯引用"的数据流跑通。
3. **实现六个记忆函数（针对 session.state）**：先只处理 `session.state` 层面的读写，不接 Mongo，验证 LLM 调用这些工具、`load_memory`/`append_memory` 等语义是否符合预期（尤其是 `replace_memory` 的唯一匹配 + 空字符串删除语义）。
4. **接入 Mongo 的 hydrate（激活时）**：四类落库记忆在会话开始时统一从 Mongo 读入 state。
5. **接入 flush-back（先做最简单的"结束时整篇覆盖"版本）**：跑通"写了新记忆 → 会话结束 → 下次激活还能读到"这个端到端闭环。
6. **升级 flush-back 为增量追加 + 乐观锁**：解决第7.3/8节提到的持久性和并发风险。
7. **加 `after_tool_callback` 的 long_run_task 自动更新逻辑**：这一步需要针对具体业务里"哪些工具调用代表任务进展"做规则设计，建议放在后面做，先用手动调用 `append_memory` 覆盖这个需求进行验证。
8. **加大小上限与清理逻辑**：`append_memory`/`write_memory`/`replace_memory` 写入后检查 `body` 大小，触发第4.3节的（按标签置信度加权的）清理。
9. **加删除操作的确认流程与并发处理**：`delete_all_memory`/`delete_memory` 的用户确认交互，以及直接同步到 Mongo（不走缓存路径）的实现。
10. **上线第4.4节的定期巡检任务（scheduled sweep）**：先实现 episodic 的 TTL 删除/晋升逻辑（规则最简单、验证价值最高），再逐步补齐 topics 的 disuse 复核、long_run_task 的僵尸任务归档、preferences 的一致性去重；巡检任务落地后同步维护好 `status` 字段（active/archived）的读取过滤（固定读取和 `load_all_memory` 默认不应返回 `archived` 状态的内容）。
11. **接入角色变化触发器**：`before_agent_callback` 里对比本次和上一次读到的部门/岗位快照，检测到变化时触发 topics 的全量复核（4.4.3），这是相对独立、可以最后再加的增强项。
